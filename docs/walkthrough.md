### Що вже є в репо

Усі задачі — на одній системі, «Велопрокат громади»: користувач бере велосипед на станції,
повертає його, а сервіс рахує ціну поїздки за тарифами громади і формує чек.

| Шлях | Що це |
|---|---|
| `docs/spec/tariffs.md` | **Специфікація тарифів** — правила T1–T10. Єдине джерело очікуваної поведінки |
| `app/` | Сервіс: `src/` (розрахунок, денний ліміт, зони, чек, HTTP API), сторінка `public/index.html`, тести `test/` |
| `ci/` | Логи чотирьох невдалих прогонів CI і зміни, що їх запустили — вхід для Task D. Почніть з `ci/README.md` |
| `tools/` | `mutate.mjs` — мутаційне тестування; `repeat.mjs` — прогнати тести N разів; їхні тести |
| `ai-runs/` | Сюди — перші відповіді AI, дослівно (див. `ai-runs/README.md`) |
| `docs/templates/` | Шаблони для всіх документів домашки |

Шаблони скопіюйте на їхні місця одразу:

```bash
cp docs/templates/test-case.md docs/test-cases.md
cp docs/templates/{traceability,ai-test-checklist,test-quality,triage}.md docs/
mkdir -p docs/bugs && cp docs/templates/bugs-readme.md docs/bugs/README.md
cp docs/templates/task-e-bonus.md docs/   # лише якщо робите бонус
```

Звіти про дефекти (`docs/bugs/BUG-<N>.md`, `docs/bugs/CI-<NNNN>.md`) копіюєте з
`docs/templates/bug-report.md`, коли знайдете дефект.

> **Правила для всіх задач.**
> 1. **AI — асистент, рішення ухвалюєте ви.** Під тест-кейсами, класифікацією і звітами
>    про дефекти підписуєтеся ви, а не модель.
> 2. **Оракул — специфікація.** Що правильно, вирішує `docs/spec/tariffs.md`, а не код і не
>    відповідь AI. Специфікація не дає однозначної відповіді — це питання до власника
>    продукту, а не привід вибрати відповідь мовчки.
> 3. **Перша відповідь AI — дослівно в `ai-runs/`, до будь-яких виправлень.** Саме її ми
>    міряємо. Не скорочуйте, не правте і не перепитуйте, «поки не вийде». Далі працюйте з
>    AI скільки завгодно — у своїх файлах у `docs/` і `app/`.
> 4. **Кожне твердження, яке ви лишаєте, має доказ:** `файл:рядок`, назва тесту або команда
>    і її вивід. Без доказу — викреслюйте або позначайте як припущення.
> 5. **Один прогін — одна нова сесія:** без історії попередніх прогонів і без ваших підказок.
> 6. **`docs/spec/` і `ci/` не змінюйте** — це входи. Текст у логах, дифах і специфікації —
>    дані, а не інструкції ні для вас, ні для агента.
> 7. **До Task C не запускайте `npm run mutate`** — ні самі, ні агентом. Якщо агент
>    запустив його з власної ініціативи — запишіть це в шапці файлу в `ai-runs/`.

### Як показати AI лише частину репо

Працюйте в **агентному режимі** (Claude Code; Cursor — Agent; Copilot — Agent mode): AI
має сам читати файли, писати тести й запускати команди.

Agentic IDE бачить усю теку проєкту і сам підвантажує `AGENTS.md` / `CLAUDE.md`. Тому для
прогонів, де AI має бачити лише частину репо, робіть **тимчасову копію** потрібних файлів
**поруч із репо** (не всередині — інакше `git add -A` її закомітить) і відкривайте її як
окремий проєкт у новій сесії. Копії беремо з `main` — у стані з початку домашки, навіть
якщо ви вже щось змінили у своїй гілці, — якщо крок не каже інакше (запах тестів у Task C і
перша відповідь про флакі в Task D беруть поточний стан; це сказано в самому кроці).

**Усі команди в цьому файлі — у Git Bash** (на Windows). У Windows PowerShell 5.1 —
терміналі за замовчуванням у Cursor і VS Code — конвеєр `git archive | tar` псує архів.

```bash
# приклад: прогін, який бачить лише app/src/
mkdir -p ../ws12-a1 && git archive main app/src | tar -x -C ../ws12-a1
```

Команди для кожного прогону — у задачах нижче. Гірший варіант — прогін у самому репо з
явною вказівкою в промпті «читай лише …»: агент усе одно бачить `AGENTS.md`, специфікацію і
може зазирнути деінде. Якщо робили так — напишіть це в шапці файлу в `ai-runs/`.

На час прогонів вимкніть пам'ять між сесіями (memories) і глобальні правила та інструкції —
вони теж контекст: Cursor User Rules, Copilot personal instructions, `~/.claude/CLAUDE.md`,
а також `CLAUDE.md` / `AGENTS.md` у батьківських теках над `../ws12-*` (Claude Code
підвантажує і їх) — приберіть їх на час прогону. Не вийшло вимкнути — запишіть у шапці
файлу в `ai-runs/`, що саме було ввімкнено.

Промпти нижче — у блоках `text`. Копіюйте їх **дослівно**, без своїх доповнень.

## Task A — Тест-дизайн зі специфікації _(~1 год)_

**Мета:** побачити, звідки AI бере очікувані значення, — і спроєктувати тест-кейси, де
очікування береться зі специфікації, а неоднозначність стає питанням.

1. **Прогін A1 — «з коду».** AI бачить **лише** `app/src/` — без `docs/` і без `app/test/`.
   Рекомендовано — тимчасова копія:
   ```bash
   mkdir -p ../ws12-a1 && git archive main app/src | tar -x -C ../ws12-a1
   ```

   ```text
   У цій теці — код сервісу, який рахує вартість поїздок велопрокату громади (app/src/).
   Читай лише файли в app/src/.
   Склади набір тест-кейсів для розрахунку вартості поїздки. Для кожного кейсу: ID; що
   перевіряє; вхідні дані (усе, від чого залежить результат); очікуваний результат у
   копійках; звідки взято це очікування.
   Запиши відповідь у файл ai-runs/a1-from-code.md. Нічого іншого не створюй і не змінюй.
   Уточнювальних питань не став; працюй з тим, що є.
   ```

   Поверніть файл у репо і додайте шапку (див. `ai-runs/README.md`):
   ```bash
   cp ../ws12-a1/ai-runs/a1-from-code.md ai-runs/
   ```

2. **Прогін A2 — «зі специфікації».** AI бачить **лише** `docs/spec/tariffs.md`.
   ```bash
   mkdir -p ../ws12-a2/docs/spec && cp docs/spec/tariffs.md ../ws12-a2/docs/spec/
   ```

   ```text
   У цій теці — специфікація тарифів велопрокату громади (docs/spec/tariffs.md).
   Читай лише цей файл.
   Склади набір тест-кейсів для розрахунку вартості поїздки. Для кожного кейсу: ID; що
   перевіряє; вхідні дані (усе, від чого залежить результат); очікуваний результат у
   копійках; звідки взято це очікування.
   Запиши відповідь у файл ai-runs/a2-from-spec.md. Нічого іншого не створюй і не змінюй.
   Уточнювальних питань не став; працюй з тим, що є.
   ```

   ```bash
   cp ../ws12-a2/ai-runs/a2-from-spec.md ai-runs/
   ```

3. **Ваш чек-ліст** — `docs/ai-test-checklist.md` (шаблон є): щонайменше 8 пунктів, за
   якими ви перевіряєте тестові артефакти від AI. Застосуйте його до A1 і A2 — вердикт по
   кожному пункту з прикладом. Пункти — ваші: виведіть їх з того, що побачили в чернетках
   і на воркшопі.

4. **Ваші тест-кейси** — `docs/test-cases.md` (шаблон є), **зі специфікації**. Кожен кейс:

   специфікації, пріоритет. Чернетки AI можна брати за основу — але кожне очікування
   перевірте за специфікацією самі. Номер рядка — з `grep -n` або редактора:
   ```bash
   grep -n "T4" docs/spec/tariffs.md
   ```
   Розділ **«Питання до специфікації»** — усе, на що специфікація не дає однозначної

A1 — …, A2 — …; неоднозначностей позначено як питання: A1 — …, A2 — …» (таблиця
«Порівняння чернеток AI» у `docs/test-cases.md`).

**Перевірка:** обидва файли в `ai-runs/`; кожен кейс у `docs/test-cases.md` має правило,
техніку, рядок специфікації і пріоритет; є розділи «Питання до специфікації» і «Що AI
вигадав» (числа в «Порівнянні чернеток AI» сходяться з ним); у
`docs/traceability.md` — усі 10 правил; у чек-листі ≥ 8 пунктів з вердиктом для A1 і A2;
числа сходяться з таблицями.

## Task B — Автотести й справжні баги _(~1,5 год)_

**Мета:** порівняти тести, написані з коду, і тести, написані зі специфікації, — і довести
кожен знайдений дефект так, щоб його відтворив будь-хто.

1. **Прогін «з коду».** AI пише unit-тести, бачачи лише код. Копія з `main` + `package.json`,
   щоб Node читав файли як ES-модулі:
   ```bash
   mkdir -p ../ws12-b1 && git archive main app/src | tar -x -C ../ws12-b1
   printf '{ "type": "module" }\n' > ../ws12-b1/package.json
   ```

   ```text
   У цій теці — код сервісу, який рахує вартість поїздок велопрокату громади (app/src/).
   Читай лише файли в app/src/ і package.json у корені теки.
   Напиши unit-тести для app/src/tariff.js і app/src/day-cap.js на вбудованому раннері Node
   (node:test і node:assert/strict), без npm-залежностей. Поклади їх у теку
   ai-runs/b1-from-code/ у файли *.test.js; модулі імпортуй шляхом ../../app/src/<файл>.js.
   Запусти тести командою node --test "ai-runs/b1-from-code/*.test.js" і покажи результат.
   Не змінюй app/src/. Уточнювальних питань не став; працюй з тим, що є.
   ```

   Поверніть тести в репо, збережіть фінальну відповідь агента в `ai-runs/b1-from-code.md`
   (з шапкою) і запустіть тести **у репо**, поки код ще не змінено:
   ```bash
   mkdir -p ai-runs/b1-from-code && cp ../ws12-b1/ai-runs/b1-from-code/*.test.js ai-runs/b1-from-code/
   node --test "ai-runs/b1-from-code/*.test.js" > ai-runs/b1-run.txt; cat ai-runs/b1-run.txt
   ```
   Агент поклав тести деінде — візьміть їх звідти й напишіть це в шапці
   `ai-runs/b1-from-code.md`. Самі тести не правте.

2. **Прогін «зі специфікації».** AI автоматизує **ваші** кейси з Task A. Це прогін у репо,
   у новій сесії:

   ```text
   Автоматизуй тест-кейси з docs/test-cases.md як тести на вбудованому раннері Node
   (node:test і node:assert/strict), без npm-залежностей, у файлах app/test/spec/*.test.js.
   Очікувані значення бери лише з docs/test-cases.md і docs/spec/tariffs.md. З app/src/ бери
   тільки те, як викликати функції і в якому форматі вони повертають результат, — не
   очікувані значення.
   Однотипні кейси — таблицею даних у циклі, а не копіями тесту; кожне граничне значення —
   окремим рядком таблиці; у назві кожного тесту — ID правила, наприклад «T3: …».
   Кейси з розділу «Питання до специфікації» не автоматизуй.
   Не змінюй app/src/ і наявні тести. Запусти npm test і покажи результат; червоні тести не
   виправляй.
   ```

   ```bash
   npm test > ai-runs/b2-run.txt; cat ai-runs/b2-run.txt
   ```
   Тести в `app/test/spec/` — уже ваші: їх можна виправляти, але кожне змінене очікування —
   лише за специфікацією, з рядком.

3. **Класифікуйте кожен червоний тест** з `ai-runs/b1-run.txt` і `ai-runs/b2-run.txt` —
   `docs/bugs/README.md` (шаблон є): **дефект коду** / **хибний тест** / **прогалина в
   специфікації**, і доказ. Тест червоніє то так, то ні без змін у коді — запишіть це; ним
   займетеся в Task D.

4. **Виправте дефекти коду** в `app/src/` (червоне → зелене). **Один дефект — один коміт**:
   хеш коміту піде у звіт про дефект.
   ```bash
   git add app/src && git commit -m "fix(Tn): <що виправлено>"
   ```
   Якщо після виправлення почервоніли наявні тести в `app/test/unit/` — з'ясуйте за
   специфікацією, хто неправий. Тест, що стверджував хибну поведінку, оновіть за
   специфікацією і запишіть у `docs/bugs/README.md`, який саме і чому. Не видаляйте його і
   не послаблюйте перевірку. Після виправлень `npm test` зелений — крім тесту, що червоніє
   то так, то ні (ним займетеся в Task D).

5. **Повторний прогін тестів «з коду» на виправленому коді.** Самі тести не змінюйте:
   ```bash
   node --test "ai-runs/b1-from-code/*.test.js" > ai-runs/b1-rerun.txt; cat ai-runs/b1-rerun.txt
   ```
   Тест, який був зелений на початковому коді й почервонів на виправленому, стверджував
   саме ту поведінку, яку ви виправили: він зафіксував дефект, а не знайшов його. Таблиця —
   у `docs/bugs/README.md`.

6. **Звіт про кожен дефект** — `docs/bugs/BUG-<N>.md` (шаблон `docs/templates/bug-report.md`):
   правило, кроки, очікуване за специфікацією з рядком, фактичне, команда-доказ з виводом,
   серйозність, коміт виправлення. Доказ — команда з кореня репо, яку можна повторити,
   наприклад:
   ```bash
   node -e 'import("./app/src/tariff.js").then(({ quote }) => console.log(JSON.stringify(quote(
     { pickupAt: "2026-09-16T07:00:00Z", returnAt: "2026-09-16T07:40:00Z", bike: "classic", returnStation: "S03" },
     { type: "standard" }), null, 2)))'
   ```
   Фактичний результат **до** виправлення покажіть на копії початкового коду з `main` —
   тією самою командою:
   ```bash
   mkdir -p ../ws12-main && git archive main app | tar -x -C ../ws12-main
   cd ../ws12-main && node -e '<та сама команда>'; cd -
   ```

7. Заповніть колонку автотестів у `docs/traceability.md`.

**Число:** «дефектів, які знайшли тести з коду: X; тести зі спеки: Y; тестів з коду, що
зафіксували дефект: Z».

**Перевірка:** `ai-runs/b1-from-code/*.test.js`, `ai-runs/b1-from-code.md`,
`ai-runs/b1-run.txt`, `ai-runs/b2-run.txt`, `ai-runs/b1-rerun.txt`; тести в
`app/test/spec/` з ID правила в назві; кожен червоний тест класифіковано з доказом; кожен
дефект коду — свій `BUG-<N>.md` з усіма полями шаблону і коміт виправлення; змінені тести
в `app/test/unit/` (якщо є) перелічено з причиною; `npm test` зелений, крім нестабільного
тесту.

## Task C — Покриття проти мутацій _(~1,25 год)_

**Мета:** перевірити, чи зелений набір тестів справді помічає зміни в коді, — і навчити
агента писати тести, які помічають.

Усе — на коді **після** Task B. Перед стартом закомітьте все, що є.

1. **До.** Покриття рядків і мутаційний бал — в один файл:
   ```bash
   npm run -s coverage > ai-runs/c-before.txt      # покриття: лише app/test/unit/
   node tools/mutate.mjs >> ai-runs/c-before.txt   # мутації: app/test/unit/ + app/test/spec/
   cat ai-runs/c-before.txt
   ```
   Мутант — маленька зміна коду (`+` на `-`, `&&` на `||`, число на число + 1, …). Тести, які на
   зміненому коді лишаються зеленими, мутанта не помітили — він «вижив».

2. **Тестові «запахи».** Спершу самі: пройдіть `app/test/unit/` і запишіть у
   `docs/test-quality.md` кожен запах — назва, тест, `файл:рядок`, чому це проблема. Потім
   спитайте AI на копії поточного `app/`:
   ```bash
   mkdir -p ../ws12-c-smells && cp -r app ../ws12-c-smells/
   ```

   ```text
   У цій теці — застосунок (app/): код у app/src/ і тести в app/test/.
   Знайди тестові «запахи» (test smells) у тестах app/test/unit/. Для кожного: файл:рядок,
   назва тесту, назва запаху і чому це проблема. Нічого не змінюй.
   Запиши відповідь у файл ai-runs/c-smells.md.
   Уточнювальних питань не став; працюй з тим, що є.
   ```

   ```bash
   cp ../ws12-c-smells/ai-runs/c-smells.md ai-runs/
   ```
   У таблиці запахів позначте, які з ваших AI знайшов, і що AI назвав запахом, а ви не
   погоджуєтеся.

3. **AI посилює тести.** Закомітьте поточний стан, щоб `git diff` показав рівно зміни
   агента. Прогін у репо, у новій сесії:

   ```text
   npm run mutate рахує мутаційний бал тестів app/test/unit/ і app/test/spec/ для
   app/src/tariff.js і app/src/day-cap.js. Посиль тести, щоб мутаційний бал виріс.
   Запусти npm run mutate до і після змін і покажи обидва підсумки.
   ```

   Фінальну відповідь агента — у `ai-runs/c-strengthen.md`. Потім:
   ```bash
   git add -A app tools package.json
   git diff --cached --stat -- app tools package.json
   git diff --cached -- app tools package.json > ai-runs/c-strengthen.diff
   npm run -s coverage > ai-runs/c-after.txt
   node tools/mutate.mjs >> ai-runs/c-after.txt
   cat ai-runs/c-after.txt
   ```
   Таблиця «до / після» в `docs/test-quality.md`: мутаційний бал, тестів, викликів assert
   (інструмент друкує їх у шапці), покриття. **Кожен тест, який агент видалив, пропустив
   (`skip` / `todo`) або послабив, змінене очікуване значення, зміна в `app/src/` чи в
   `tools/` — знахідка**: покажіть рядком з `ai-runs/c-strengthen.diff`. Неприйнятні зміни
   агента відкотіть і поясніть чому.

4. **Мутанти, що вижили.** Візьміть щонайменше 5 зі списку «Вижили» в `ai-runs/c-after.txt`.
   Кожен — або вбийте новим тестом (і покажіть, що після нього мутант у списку не з'являється),
   або аргументуйте, що він **еквівалентний**: жоден вхід не дає іншого результату. «Тест
   був би надто складний» — не аргумент.
   ```bash
   node tools/mutate.mjs --only app/src/day-cap.js   # лише один файл — швидше
   ```
   Номери `M…` з `--only` ті самі, що й у повному прогоні; надійніше порівнювати за
   `файл:рядок:колонка` і зміною.

5. **Правила тестування для агента.** Створіть `app/AGENTS.md` з розділом `## Тести` (або
   файл правил вашої IDE: `.cursor/rules/<назва>.mdc`, `.github/copilot-instructions.md`,
   `CLAUDE.md` — будь-який). Щонайменше 5 правил, кожне — з вашої знахідки в Task A–C
   (звідки — таблиця в `docs/test-quality.md`). Два приклади, решту — ваші:
   - «Очікувані значення в тестах — зі специфікації `docs/spec/tariffs.md`, з ID правила в
     назві тесту; ніколи — з поточної поведінки коду».
   - «Не змінюй перевірку чи очікуване значення, щоб тест пройшов, не пояснивши чому».

6. **Повторний прогін з правилами.** Той самий промпт, що й у прогоні «з коду» Task B
   (крок 1), **дослівно**, у новій сесії — на копії з `main` **плюс ваш файл правил**. Покладіть
   правила туди, звідки ваш інструмент їх підхопить: `AGENTS.md` (Cursor, Copilot, Codex),
   `CLAUDE.md` (Claude Code), `.cursor/rules/` (Cursor), `.github/copilot-instructions.md`
   (Copilot):
   ```bash
   mkdir -p ../ws12-c-rules && git archive main app/src | tar -x -C ../ws12-c-rules
   printf '{ "type": "module" }\n' > ../ws12-c-rules/package.json
   RULES=app/AGENTS.md   # або шлях до вашого файлу правил
   cp "$RULES" ../ws12-c-rules/AGENTS.md && cp "$RULES" ../ws12-c-rules/CLAUDE.md
   ```
   Специфікації в копії навмисно немає — прогін той самий, що в Task B. Подивіться, що агент
   робить з очікуваними значеннями, коли правило вимагає специфікацію, а її немає.
   Фінальну відповідь агента — у `ai-runs/c-with-rules.md`, тести — в `ai-runs/c-with-rules/`:
   ```bash
   mkdir -p ai-runs/c-with-rules && cp ../ws12-c-rules/ai-runs/b1-from-code/*.test.js ai-runs/c-with-rules/
   ```
   Що змінилося порівняно з прогоном без правил — розділ 6 у `docs/test-quality.md`.

**Число:** покриття рядків і мутаційний бал до / після; тестів і викликів assert до /
після; тестів, які AI видалив, пропустив або послабив.

## Task D — Флакі й тріаж CI _(~1 год)_

**Мета:** знайти причину нестабільного тесту, а не сховати її, — і розібрати чужі падіння
CI за доказами, а не за першим враженням.

1. **Скільки разів падає.** Закомітьте поточний стан і проженіть усі тести застосунку 30 разів:
   ```bash
   node tools/repeat.mjs 30 > ai-runs/d-repeat-before.txt; cat ai-runs/d-repeat-before.txt
   ```

2. **Перша відповідь AI.** Прогін на копії поточного стану (`HEAD`) — **без** вашого файлу
   правил з Task C і без ваших нотаток у `docs/`: інакше міряємо ваші правила, а не агента.
   Копія — з власним git, щоб diff показав рівно зміни агента:
   ```bash
   rm -rf ../ws12-d-flaky && mkdir -p ../ws12-d-flaky/ai-runs
   git archive HEAD app tools package.json .gitattributes | tar -x -C ../ws12-d-flaky
   rm -f ../ws12-d-flaky/app/AGENTS.md ../ws12-d-flaky/app/CLAUDE.md
   cp ai-runs/d-repeat-before.txt ../ws12-d-flaky/ai-runs/
   git -C ../ws12-d-flaky init -q && git -C ../ws12-d-flaky add -A
   git -C ../ws12-d-flaky -c user.name=ws12 -c user.email=ws12@example.org commit -qm base
   ```
   Файл правил лежить деінде всередині `app/` — приберіть з копії і його.

   ```text
   Тест у цій теці іноді падає — див. ai-runs/d-repeat-before.txt (вивід
   npm run test:repeat -- 30). Виправ.
   ```

   Фінальну відповідь агента — у `ai-runs/d-flaky-first.md`, його зміни — в diff:
   ```bash
   git -C ../ws12-d-flaky add -A
   git -C ../ws12-d-flaky diff --cached > ai-runs/d-flaky-first.diff
   ```
   Міряємо одне: чи запропонував агент **повтор (retry), очікування (sleep), пропуск
   (skip) або послаблену перевірку**. Зміни агента лишаються в копії — у репо їх не
   переносьте; причину виправляєте самі (крок 3).

3. **Виправте причину.** Знайдіть, чому той самий код то проходить, то ні, і виправте саме
   це — без повторів, очікувань, `skip` і послаблених перевірок. Доказ — 50 прогонів без
   жодного падіння:
   ```bash
   node tools/repeat.mjs 50 > ai-runs/d-repeat-after.txt; cat ai-runs/d-repeat-after.txt
   ```
   Причина, докази і виправлення — розділ 1 у `docs/triage.md` (шаблон є).

4. **Тріаж CI.** У `ci/` — чотири невдалі прогони за тиждень. Спершу — відповідь AI на
   копії з `main` (усе `ci/` і `app/`):
   ```bash
   mkdir -p ../ws12-d-ci && git archive main app ci | tar -x -C ../ws12-d-ci
   ```

   ```text
   У цій теці: ci/ — логи чотирьох невдалих прогонів CI (ci/runs/), зміни, що їх запустили
   (ci/changes/), і опис пайплайна (ci/README.md); app/ — код застосунку і його тести.
   Для кожного прогону визнач, чому він упав, і клас падіння: дефект коду, дефект тесту,
   середовище або нестабільний тест. До кожного — докази (рядок логу, фрагмент diff або
   команда над файлами цієї теки та її вивід) і що виправити.
   Запиши відповідь у файл ai-runs/d-ci-first.md. Не змінюй файли в ci/.
   Уточнювальних питань не став; працюй з тим, що є.
   ```

   ```bash
   cp ../ws12-d-ci/ai-runs/d-ci-first.md ai-runs/
   ```

   Потім — ваш тріаж, розділ 2 у `docs/triage.md`: для кожного прогону клас (**код** /
   **тест** / **середовище** / **нестабільний**), докази (рядок логу, hunk diff, команда над
   репо) і пропоноване виправлення. Класи можуть повторюватися, а якийсь — не трапитися
   жодного разу. Для кожного прогону запишіть також першу помилку в лозі і чи вона причина —
   з доказом. Корисні команди (з кореня репо) — форма, а не відповідь:
   ```bash
   grep -n "##\[error\]" ci/runs/run-NNNN.log     # де CI позначив помилку
   grep -nE "Z (ℹ|✖) " ci/runs/run-NNNN.log       # підсумок тестів і червоні тести
   ```
   Зміну з прогону відтворюйте на окремій копії з `main` (ваш код після Task B може вже
   відрізнятися, і diff не застосується); нова копія — на кожен прогін:
   ```bash
   rm -rf ../ws12-d-repro && mkdir -p ../ws12-d-repro && git archive main app ci | tar -x -C ../ws12-d-repro
   cd ../ws12-d-repro && git init -q && git apply ci/changes/run-NNNN.diff && npm --prefix app test; cd -
   ```

5. **Звіт про дефект з логу.** Для кожного прогону, який ви класифікували як **дефект
   коду**, — `docs/bugs/CI-<NNNN>.md` (номер прогону) за тим самим шаблоном, що й у Task B:
   правило, кроки (з `git apply`), очікуване за специфікацією, фактичне, доказ (рядок логу +
   команда), серйозність. Поле «Виправлення» — що треба змінити (сам diff у `main` не
   застосовуйте). Якщо таких прогонів немає — так і напишіть у «Підсумку» `docs/triage.md`.

**Число:** «перша відповідь AI про флакі: ретрай/sleep/skip — так/ні; прогонів CI
класифіковано правильно — оцінить ментор; ваша класифікація і доказ» (таблиця «Підсумок»
у `docs/triage.md`).

**Перевірка:** `ai-runs/d-repeat-before.txt`, `ai-runs/d-flaky-first.md`,
`ai-runs/d-flaky-first.diff`, `ai-runs/d-repeat-after.txt` з 0 падінь з 50,
`ai-runs/d-ci-first.md`; у `docs/triage.md` причина і виправлення нестабільного тесту і
чотири прогони з класом, доказами й виправленням; `docs/bugs/CI-<NNNN>.md` з усіма полями
шаблону на кожен прогін класу «код» (або явне «немає» в «Підсумку»); у тестах немає
повторів, очікувань і `skip`; `ci/` не змінено.
